# Beta report · 2026-10-17

Real-browser end-to-end test of the Remaster Suite in **Chromium 153.0.8010.0 (headless, Debian 12.14)**.
Driven over the Chrome DevTools Protocol with trusted input events (real clicks,
real drops, real downloads). Generated by `node tests/beta/beta.js`.

## The machine

2 × Intel(R) Xeon(R) Processor @ 2.60GHz · Chromium 153.0.8010.0 (headless, Debian 12.14).

On this machine the analyser reads **59.3 ms per second of stereo audio**
(17× realtime). That is the number the two scale rows are
calibrated against, and the reason they are calibrated at all: the same code measured
a three-minute take in 1.7 s on the workstation that wrote the first report and needs
10.7 s here, and a row that means *the app got slower* on one
machine and *the room got colder* on another is not a measurement.

## Harness notes

- Device emulation is viewport, device scale factor and touch input — the two phones are
  `Emulation.setDeviceMetricsOverride` plus `setTouchEmulationEnabled`, and every row that
  touches something really touches it (`Input.dispatchTouchEvent`, the same input path a
  thumb uses). The user-agent is deliberately *not* forged: the browser is Chromium, the app
  decides what it is running on from the pointer, and a faked device string would only make
  the page lie to itself.
- The carousel rows never write a scroll offset. A swipe is a real finger: touch down, fourteen
  move events, up — and then the compositor's own scrolling and CSS scroll-snap decide where
  the rack lands. A row that set `scrollLeft` would pass on a rack that cannot be swiped.
- The visual baselines are only meaningful because the harness is deterministic: Chromium runs
  with `--disable-lcd-text` and `--disable-font-subpixel-positioning` (two loads of the same
  page differ by ~9 000 antialiased text pixels without them, by zero with them), and every run
  gets its own `--user-data-dir`. That last one is not tidiness: a second Chromium on a profile
  another one is using wedges the first one's OPFS worker — its storage calls never return —
  which surfaces much later as a render that sits at 100 % forever and a Magic Fix button that
  refuses every further tap. One profile per run, pruned by age.
- The baseline diff itself is tested before it is trusted: two images whose right answer is known
  by construction (a 24×16 rectangle moved, a 1/255 step, a size mismatch) must produce exactly
  the expected counts, and the difference picture must mark exactly those pixels.
- The suite drives a packaged headless Chromium (`@sparticuz/chromium`, an optional
  dev dependency) over the raw DevTools protocol — no puppeteer needed.
- Awaiting the MP3 render through `Runtime.evaluate`'s `awaitPromise` deadlocks in
  this headless sandbox (page and Node both idle; isolated repros with programmatic
  clicks pass). The suite therefore uses fire-and-forget + polling for that one
  call, which is equally strict: the promise must settle and the page must keep
  answering.
- The recordings are the same synthesised fixtures the node suites use (garage session,
  cassette, vinyl rip, low-bitrate) — built with `tests/harness.js`, served to the page on a
  loopback port and dropped as real files. A page-local fake would only test the fake.
- Analysis/render timings are sandbox-CPU numbers; real hardware is faster.
- The two scale rows are **calibrated against this machine and this run**: a 30-second
  recording goes through the identical instrumented path seconds before the three-minute
  one, and the rows hold the app to *that* rate (work may not grow faster than the file)
  plus a floor in x realtime. Both rates travel with the row, so a faster machine is held
  to a faster number and a slower one is not failed for being slow.
- The upload path is timed phase by phase (decode · measurement · preview render · preview
  measurement) by wrapping the app from the test, so a slowdown can be attributed. A wrapper
  must not change the contract of the thing it wraps: `analyzeChannels` is synchronous and
  its caller reads `.chips` and `.score` straight off the value returned, so it gets a
  synchrony-preserving wrapper while the four asynchronous stages get an awaiting one.
  Wrapping it in an `async` function cost this suite a day: the app then received a Promise,
  `card.afterScore` came out `undefined`, the card painted "43 / 100" instead of "43 → 80 /
  100", and the row read as an app defect that did not exist.
- The GUI rows drive the real controls: a slider is moved by setting its value and firing
  `input` and `change`, a select by firing `change`, a button by a trusted mouse event at
  its own coordinates. No row calls an app function in place of the listener it tests.
- The file picker is driven with DevTools' `DOM.setFileInputFiles` on a real WAV on disk,
  and the export round trip drops the app's own MP3 back in as a `File` for the browser's
  own decoder — a page-local `AudioBuffer` would test neither.
